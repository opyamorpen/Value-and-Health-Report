# ONES 应用健康度标准

> 规则版本：`health-standard-v0.1`（草案）
> 依据：根目录 `README.md` 规格 + `docs/evidence-matrix.md`（v7.22.1 实测证据）
> 本标准定义 12 个能力维度的成熟度判定规则、阈值、证据来源与降级规则。所有阈值由规则版本控制；快照生成后不可变，调整阈值需发布新规则版本。

## 1. 设计原则

1. **团队级聚合**：所有判定基于团队级聚合数据，不出现个人排名或人效评价。
2. **OpenAPI 优先**：公共 OpenAPI 能取得的证据不使用页面内部接口；内部接口仅作为 CapabilityDetector 的兜底，必须声明版本、校验响应结构，失败时降级为 `无法核验`。
3. **证据可追溯**：每个判定结果携带 `status / source / collectedAt / coverage / confidence / ruleVersion` 与证据引用（`EvidenceRef`），不呈现无法追溯的结论。
4. **不可核验 ≠ 未配置**：接口失败、漂移、权限不足一律判 `无法核验`，绝不因探测失败而降低成熟度。
5. **旁路状态不参与成熟度**：`未购买 / 不适用 / 无法核验` 不进入成熟度统计；未购模块单独进入增购机会建议。
6. **真实研发场景导向**：`形成闭环` 的判定依据是真实研发管理场景中的跨模块可追溯链（见 §3），不是简单的功能点击。

## 2. 状态定义与通用阈值

| 状态 | 定义 | 进入条件 |
| --- | --- | --- |
| `未配置` | 能力所需的配置对象不存在 | 配置证据 = 0 |
| `已配置未活跃` | 配置存在，周期内关键行为未达活跃阈值 | 配置 ≥ 1 且（行为 < A 或 持续性 < S） |
| `活跃使用` | 周期内关键行为达到阈值且有持续性 | 行为 ≥ A 且 ≥ S 个自然周有行为 |
| `形成闭环` | 活跃使用，且存在跨模块可追溯链 | 活跃使用 且 完整链 ≥ C |
| `未购买` | 组织未购买该模块 | 见 §5 |
| `不适用` | 该维度与团队业务场景无关 | 见 §6 |
| `无法核验` | 数据源失败/漂移/权限不足 | 见 §7 |

通用阈值（90 天周期基线）：

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| A | 活跃行为阈值：周期内关键行为次数 | 10（高基数维度 30，见 §4） |
| S | 持续性：有行为的不同自然周数 | 2 |
| C | 闭环链最小样本数 | 2 |
| Q | 统计指标最小样本量 | 5（低于则该指标显示「未知」） |

注：周期可配置（默认近 90 天对比前 90 天）；A/S 阈值随周期长度等比缩放（如 30 天周期 A=3, S=1）。

## 3. 闭环链定义（真实研发场景）

`形成闭环` 的判定依据是以下跨模块可追溯链在周期内真实存在（每条链需 ≥ C 个样本）：

| 链路 | 场景 | 追溯证据 |
| --- | --- | --- |
| L1 需求交付链 | 需求进入迭代 → 迭代完成 → 工作项终态 →（可选）关联发布 | Sprint 终态 + 工作项终态 + 发布关联字段 |
| L2 质量闭环链 | 用例执行发现缺陷 → 缺陷修复 → 回归验证 | 测试情况关联 + 缺陷生命周期 |
| L3 代码追溯链 | 提交关联工作项 → MR 合并 → 流水线成功 → 工作项/发布完成 | devopsTasksCommits + PR state + pipelineRun.status |
| L4 工时管理链 | 预估工时 → 实际登记 → 用于排期/资源视图 | timesEstimated + timesSpent + 资源视图使用 |
| L5 知识沉淀链 | 工作项关联 Wiki 页面（交付物/文档沉淀） | 工作项 field048 关联 Wiki |
| L6 服务协同链 | Desk 工单 → 处理 → 解决（→ 转缺陷进入研发） | 工单生命周期 + 关联缺陷 |
| L7 自动化链 | 自动化规则触发 → 业务对象自动变更 | automationLog + 对象变更记录 |

一个维度的闭环判定 = 该维度相关链路是否成立（见 §4 各维度「闭环」列）。

## 4. 维度判定规则

每个维度给出：配置证据（什么算已配置）、关键行为（什么算活跃，含阈值 A）、闭环证据（对应 §3 哪条链）、数据源（O=OpenAPI，I=内部接口，编号见 evidence-matrix.md）。

### D1 项目与工作项流程

- **配置**：团队项目数 ≥ 1（O-A1）。基线能力；项目数 = 0 才判 `未配置`。
- **活跃**（A=30）：周期内工作项创建数 + 状态流转次数（changelog，排除机器人）。
- **闭环**：L1 链——周期内完成「创建 → 首次进入终态」全生命周期的工作项 ≥ C，且存在重开等真实管理行为。
- **数据源**：O-A1/A3/A4。交付周期 P50/P75 按「创建 → 首次完成」计算，样本 < Q 显示未知。

### D2 Sprint、看板与敏捷执行

- **配置**：存在 Sprint 对象（O-A2）。
- **活跃**：周期内工作项移入 Sprint 的行为 + 执行中 Sprint 内的工作项变更 ≥ A。
- **闭环**：L1 链——周期内 ≥ C 个 Sprint 进入终态（完成/归档），且按期完成率可计算（Sprint 有起止时间与完成工作项）。
- **数据源**：O-A2 + changelog（O-A4）中的 sprint 字段流转。连续迭代趋势 = 周期内终态 Sprint 的分布。

### D3 Wiki 与知识协作

- **配置**：Wiki 空间数 ≥ 1（O-A7）。
- **活跃**：周期内页面新建/编辑 ≥ A（页面编辑时间来源见 T3）。
- **闭环**：L5 链——周期内有工作项关联 Wiki 页面（工作项 field048 有值）≥ C。
- **数据源**：O-A7/A8；页面编辑明细待 T3 验证后补充。

### D4 Test 与质量闭环

- **配置**：测试用例库 ≥ 1（O-A9）。
- **活跃**：周期内测试执行行为 ≥ A（执行数据来源见 T4，OpenAPI 仅提供用例库）。
- **闭环**：L2 链——周期内 ≥ C 个缺陷关联用例/测试情况有数据，且缺陷完成「发现 → 修复 → 验证」生命周期。
- **数据源**：O-A9；执行明细为缺口 G2。

### D5 代码仓、合并请求与流水线集成

- **配置**：已关联代码仓 ≥ 1（I-1 `devopsScmRepos`）。
- **活跃**：周期内**关联到工作项**的提交（`devopsTasksCommits.timestamp` 在周期内）或 MR 状态更新 ≥ A。注意：仅仓库有提交但未关联工作项不计入——健康度关注的是代码与研发流程的连接，不是仓库本身的提交量。
- **闭环**：L3 链——周期内 ≥ C 条：提交关联工作项 →（MR 合并 或 pipeline run 成功）→ 工作项进入终态。
- **数据源**：I-1/I-2（graphql Task / repo-data-key）。OpenAPI 无对应端点（缺口 G1）。
- **示例**（v7.22.1 实测，团队 VAVx7WoU）：工作项 GCSX-7982 有 5 条关联提交 + 1 个关联 MR（`devopsCommitCount=5, devopsPullRequestsCount=1`），提交含 author/hash/message/repo/branch/timestamp。

### D6 工时、资源与排期

- **配置**：存在工时预估记录（O-A5）或团队工时已启用。
- **活跃**：周期内工时登记（timesSpent）条数 ≥ A。
- **闭环**：L4 链——预估与实际工时同时存在的工作项占比可计算，且资源/排期视图有使用（来源见 T6）。
- **数据源**：O-A5/A6。参与人数按登记人去重（排除机器人）。

### D7 项目集与 Performance

- **配置**：存在项目集对象（数据源见 T7）。
- **活跃**：周期内项目集结构/内容有更新。
- **闭环**：项目 → 项目集 → 效能报表产出的使用证据 ≥ C。
- **数据源**：内部接口（缺口 G3）。

### D8 流程自动化

- **配置**：启用状态的自动化规则 ≥ 1（I-3 `automationRules`）。
- **活跃**：周期内规则触发（`automationLogs`）≥ A。
- **闭环**：L7 链——周期内 ≥ C 条自动化产生的工作项生命周期变更（如自动创建 → 自动流转至终态）。
- **数据源**：I-3。机器人创建的工作项计入吞吐量，但不计入协作参与人数（见 §8）。

### D9 Desk 服务管理

- **配置**：Desk 启用且存在工单分类（数据源见 T9）。
- **活跃**：周期内工单创建/处理 ≥ A。
- **闭环**：L6 链——周期内 ≥ C 单工单「创建 → 解决」闭环，且 SLA 达成或存在工单转缺陷。
- **数据源**：内部接口（缺口 G4）。

### D10 Account、SSO、目录与 IM 集成

- **配置**：SSO 插件已配置或存在第三方账号绑定（O-A10 部分）。
- **活跃**：周期内 SSO 登录 / 目录同步 / IM 通知行为 ≥ A（来源见 T8）。
- **闭环**：目录同步自动开通账号 + IM 机器人通知与业务事件联动 ≥ C 条。
- **数据源**：O-A10 + 内部接口。

### D11 Assistant、MCP 与 AI 能力

- **配置**：AI 模型已配置（I-4 copilot capabilities 返回已配置模型；v7.22.1 实测：未配置时工作台显示「未配置 Assistant 所需的 AI 模型」）。
- **活跃**：周期内 AI 会话/调用 ≥ A（I-4 conversations）。
- **闭环**：AI 在业务对象上的使用（工作项总结、知识问答引用业务数据）≥ C 次。
- **数据源**：I-4。

### D12 其他已购应用与版本特有能力

- 按 license 清单（O-A11 / I-5）对比已购、已安装、已授权应用。
- 首版仅报告购买与安装状态（进入增购机会分析），不做成熟度判定；版本特有能力随规则版本逐步纳入。

## 5. 购买判定（`未购买`）

- 正式路径：OpenAPI `/openapi/v2/license/apps`（scope `read:license:app`，需组织管理员）。
- 兜底路径：内部接口 `organization/{org}/bff/licenses`（I-5，无需管理员，页面自身使用）。
- 判定：模块 appID 出现在 license 列表 → 已购买；否则 `未购买`，该维度不参与健康度，进入增购机会建议（结合活跃使用证据生成建议，如「Project 活跃使用但 Test 未购买 → 建议 Test 试用」）。
- 两条路径都失败 → `无法核验`。

## 6. 不适用判定（`不适用`）

自动建议规则（由 CSM 在报告编辑页确认或覆盖，确认动作进审计日志）：

- 团队全部项目为非研发型模板（交付实施/工单/课题类）→ 代码集成、流水线建议 `不适用`。
- 团队无客服场景（无 Desk 配置）且 Desk 未购买 → Desk 建议 `不适用`。
- 无排期/资源管理诉求（无工时预估且周期内无登记）→ D6 保持成熟度判定但标注「无预估实践」。

## 7. 无法核验判定（`无法核验`）

触发条件（任一）：

1. 数据源 HTTP 失败（网络/5xx）。
2. 响应结构校验失败（接口漂移：字段缺失、类型不符）。
3. 401（token 失效且刷新后仍失败）。
4. 403（OAuth scope 不足 或 ONES 业务权限不足）。
5. 版本不匹配（目标实例版本低于探测器声明版本）。

处理：维度状态 = `无法核验`，展示最后成功采集时间与失败类别（客户版 PDF 隐藏内部错误细节）。**不得**将失败降级为 `未配置` 或 `已配置未活跃`。

## 8. 机器人过滤

- 变更日志、评论、工时的统计口径为「人工行为」，author 为系统账号时排除。
- 识别方式：消息接口的 `from: "BOT"`（v7.22.1 实测）；OpenAPI 用户模型的机器人标识字段（待 T1 验证）；已知系统账号名单（如「流程自动化」「系统」）由规则版本维护。
- 机器人**创建**的业务对象（如自动化创建的工作项）计入业务产出与吞吐量，但不计入「协作参与人数」与「人工协作行为」。

## 9. 与报告的衔接

每个维度在报告中输出：

- 状态（7 态之一）+ 当前周期 vs 前一周期的状态变化。
- 证据覆盖率（如：可核验工作项中 N% 存在代码关联）。
- 建议动作 = 下一成熟度等级的达成条件（如「已配置未活跃 → 活跃使用：将提交信息关联工作项编号，周期内达到 10 次关联提交」）。
- 样本不足（< Q）的指标显示「未知」，不推断。
