# ONES 客户价值呈现标准

> 规则版本：`value-standard-v0.2`（评审稿）
> 依据：根目录 `README.md` 规格 + `docs/evidence-matrix.md`（v7.22.1 实测证据）+ v0.1 实现复盘
> 本标准定义客户价值报告的价值模型、维度体系、指标口径、环比与价值亮点生成规则。所有阈值、映射与口径由规则版本控制；快照生成后不可变，调整需发布新规则版本。

## 1. 目标与设计原则

价值报告回答甲方一个问题：**用了 ONES 之后，给我们带来了什么？** 答案由两部分构成：

- **成果（做了什么）**：周期内完成并沉淀下来的产出——交付了多少需求、修复了多少缺陷、完成了几个迭代、沉淀了多少文档。
- **改善（变得更好了吗）**：与上一周期相比，交付速度、交付确定性、管理规范度、协作深度的可量化变化。

设计原则：

1. **双轨叙事**：绝对成果打底，环比改善做亮点。成果证明「系统在承载核心业务」，改善证明「用得越久价值越大」。
2. **团队级聚合**：不出现个人排名或人效评价（沿用 v0.1 红线）。
3. **不算 ROI**：不计算未经客户确认的节省金额，不把使用次数宣称为 ROI；价值只能以「指标改善 + 成果量化」表达。
4. **证据可追溯**：每条结论携带 `status / source / collectedAt / coverage / confidence / ruleVersion`；样本不足显示「未知」，不推断。
5. **不粉饰**：显著退步的指标如实呈现，不把下降包装成改善。
6. **数据边界**：仅使用 OpenAPI 实测可达数据（见 §7）；不可达的数据不估计、不编造。

## 2. 统一指标结构与环比标准

### 2.1 指标结构

每个价值指标统一为：

| 字段 | 含义 |
| --- | --- |
| `current` / `previous` | 当前周期值 / 对比周期值 |
| `delta` | 差值（current − previous） |
| `deltaPercent` | 数值类指标的相对变化（%） |
| `deltaPP` | 比率类指标的百分点差（pp） |
| `trendLabel` | 数值变化标签（见 §2.3） |
| `direction` | 价值方向：`up`（越高越好）/ `down`（越低越好）/ `neutral`（仅呈现） |
| `isImprovement` | 数值变化 × 价值方向解读出的「是否为改善」 |
| `sampleSize` | 支撑该指标计算的最小观测单元数 |
| `envelope` | 证据信封（status / source / collectedAt / coverage / confidence / ruleVersion） |

`isImprovement` 判定：数值上升 ∧ `direction=up`，或数值下降 ∧ `direction=down`。例：交付周期（`down`）P50 从 96h 降至 72h → 改善。`neutral` 指标不计算 `isImprovement`、不进亮点池。

### 2.2 对比基线

默认近 90 天对比前 90 天（周期可配置）。事件归属按行为发生时间：创建归创建时间（field013）、首次完成归首次终态变更时间、Sprint 完成归 finishTime/endDate。采集窗口必须同时覆盖两个周期（v0.1 采集已满足，缺的是对比周期计算）。

### 2.3 趋势标签阈值

| 指标类型 | 显著 | 略有 | 基本持平 | 特例 |
| --- | --- | --- | --- | --- |
| 数值类（计数、人数、时长） | \|Δ%\| ≥ 10% | 5% ≤ \|Δ%\| < 10% | \|Δ%\| < 5% | previous=0 且 current>0 → `新增` |
| 比率类（占比、完成率） | \|Δpp\| ≥ 5 | 2 ≤ \|Δpp\| < 5 | \|Δpp\| < 2 | — |

- 任一周期 `sampleSize < Q` → `未知`，不参与亮点池。
- `Q = 5`，不随周期长度缩放；调整需发布新规则版本。
- 周期缩短（如 30 天）时阈值不自动放宽，由规则版本统一调整。

## 3. 维度体系与指标口径

四轴九维度。每条指标给出：口径（算什么）、方向（价值方向）、样本（样本量统计单元）、数据源（O-Ax 编号见 evidence-matrix.md）。

### A 价值成果轴（做了什么）

#### A1 需求与价值交付

前置依赖：工作项类型映射（§4.1）。类型拆分不可用时本组降级为全类型口径并标注。

| 指标 | 口径 | 方向 | 样本 | 数据源 |
| --- | --- | --- | --- | --- |
| 需求创建数 | 周期内创建的需求类工作项数 | up | 计数本身 | O-A12（T14） |
| 需求交付量 | 周期内首次进入终态的需求类工作项数 | up | 计数本身 | O-A12+O-A4 |
| 需求交付周期 P50/P75 | 创建 → 首次终态时长，仅需求类 | down | 时长样本数 | O-A12+O-A4 |
| 需求按期率 | 有截止日期的需求中，首次完成 ≤ 截止 + 1 天（宽容期沿用 v0.1）的占比 | up | 有截止日期的需求数 | O-A12+O-A4 |
| 需求迭代纳入率 | 周期内交付的需求中关联过迭代的占比（sprintUuid 非空，或 changelog 存在迭代字段流转） | up | 交付需求数 | O-A12+O-A4 |

成果叙事示例：「本周期交付需求 120 个，其中 87% 纳入迭代管理」。

#### A2 缺陷与质量

| 指标 | 口径 | 方向 | 样本 | 数据源 |
| --- | --- | --- | --- | --- |
| 缺陷发现数 | 周期内创建的缺陷类工作项数 | neutral | 计数本身 | O-A12（T14） |
| 缺陷修复数 | 周期内首次进入终态的缺陷类工作项数 | up | 计数本身 | O-A12+O-A4 |
| 遗留缺陷数 | 周期内创建、报告生成时点仍处非终态的缺陷数（时点口径，见 §4.5） | down | 计数本身 | O-A12+O-A4 交叉 |
| 缺陷修复周期 P50 | 创建 → 首次终态时长，仅缺陷类 | down | 时长样本数 | O-A12+O-A4 |
| 缺陷重开率 | 周期内缺陷终态 → 非终态的重开次数 / 缺陷首次完成数 | down | 缺陷首次完成数 | O-A4 |

缺陷发现数按 `neutral` 处理：发现得多既可能是把关变严，也可能是质量变差，不做价值解读，仅呈现（评审点，见 §10）。

#### A3 敏捷迭代执行

| 指标 | 口径 | 方向 | 样本 | 数据源 |
| --- | --- | --- | --- | --- |
| Sprint 完成数 | 周期内进入终态的 Sprint 数（终态口径见 §4.2） | up | 计数本身 | O-A2 |
| Sprint 按期完成率 | 有起止日期的完成 Sprint 中，完成时间 ≤ endDate + 1 天的占比 | up | 有起止日期的完成 Sprint 数 | O-A2 |
| 迭代交付量 | 周期内完成 Sprint 承载的工作项数（总量 + 单迭代中位数，按 issue.sprintUuid 归属） | up | 完成 Sprint 数 | O-A2+O-A12 |
| 迭代节奏 | 有终态 Sprint 的不同自然周数（附周分布趋势图） | up | 完成 Sprint 数 | O-A2 |

| 指标 | 口径 | 方向 | 样本 | 数据源 |

### 3.x 统计范围（背景，非价值指标）

v0.1 的项目维度降级为报告开头的统计范围声明：活跃项目数（口径修正见 §4.4）、新建项目数、统计周期、团队。不进亮点池、不环比；项目状态分布移除（对价值叙事无贡献）。

## 4. 口径与映射规则

### 4.1 工作项类型映射（T14 前置）

类型名关键词映射（初始表，纳入规则版本，评审可调）：

- 需求：`需求` / `requirement` / `story` / `epic` / `feature`
- 缺陷：`缺陷` / `bug` / `defect`
- 任务：`任务` / `task`
- 其余 → `未分类`

映射覆盖率（已分类 / 总数）在报告口径说明中如实呈现；未分类占比 > 30% 时，类型拆分组（A1/A2 及分类型周期）整体降级为「拆分不可用」，仅保留全类型口径。

### 4.2 终态判定

- 工作项：沿用 T13 关键词约定（`done|完成|关闭|resolved|closed|finished`）。
- Sprint：status 命中终态关键词 **或** finishTime 非空（v0.1 口径修正，见 §4.4）。
- 按期宽容期：+1 天（86400000ms，沿用 v0.1）。

### 4.3 机器人过滤

沿用 `docs/health-standard.md` §8：`{{system_bot}}`、已知系统账号名单过滤；机器人创建的对象计入吞吐，不计入参与人数与人工协作行为。

### 4.4 v0.1 口径修正（文档先行定义，实现跟进）

1. **活跃项目**：周期内有工作项创建或人工变更的项目集合，按 issue.projectUuid 归并。v0.1 实现误将 issueUuid 计入集合导致虚高。
2. **Sprint 终态**：v0.1 注释声称检查 status 但实际只按 finishTime/endDate 落在周期内判断；v0.2 以「status 终态或 finishTime 非空」为准。
3. **评论数**：v0.1 硬编码 0（无真实数据源，collectCommentCount 为 issue 计数占位实现）；v0.2 不纳入协作维度，待平台提供评论 OpenAPI 后随新规则版本加入。
4. **协作中的工时登记**：v0.1 承诺但未实现；v0.2 移入 C3 工时实践维度（口径独立、可降级）。

### 4.5 时点口径说明

「遗留缺陷」等时点类指标以**报告生成时刻**的观测为准（OpenAPI 无历史时点快照，changelog 窗口外的事件不可见）。口径说明附录中如实标注：「遗留缺陷数为报告生成时点仍处非终态的统计」。

## 5. 价值亮点生成规则

1. **候选池** = 同时满足：trendLabel 为「显著」（数值类 \|Δ%\| ≥ 10% 或比率类 \|Δpp\| ≥ 5）∧ `isImprovement` ∧ 双周期样本均 ≥ Q ∧ `direction ≠ neutral`。
2. **排序与选取**：按改善幅度降序（数值类 \|Δ%\|、比率类 \|Δpp\|），取 Top 3~5；不足 3 条则如实少显示，**不硬凑**。
3. **新增实践**：`新增`（previous=0 且 current>0）单独归为「新增实践」亮点，最多 1 条，排在改善亮点之后。
4. **无显著改善回退**：全部指标无显著改善时，回退为最大绝对成果 Top 3（需求交付量、缺陷修复数、参与人数等 up 类计数）。
5. **需关注段（可选，评审点）**：显著退步（显著 ∧ 非 isImprovement）的指标最多列 2 条，中性措辞（「交付周期中位数变长 18%（72h → 85h），建议关注」）；是否进入客户版 PDF 由 CSM 在导出时选择。
6. **文案模板**：
   - 计数类改善：「{指标}提升 {Δ%}（{previous} → {current}）」
   - 比率类改善：「{指标}提升 {Δpp} 个百分点（{previous}% → {current}%）」
   - down 类改善：「{指标}缩短 {Δ%}（{previous} → {current}）」

## 6. 叙事模板（defaultNarrative v0.2）

summary 三段式，数字全部取自指标，模板固定：

1. **成果句**：本周期 {活跃项目数} 个活跃项目中，交付需求 {X} 个、修复缺陷 {Y} 个、完成迭代 {Z} 个。
2. **改善句**：与上一周期相比，{亮点 1}；{亮点 2}。（取价值亮点前 2 条；无亮点时改为「核心指标环比基本持平」）
3. **参与句**：{P} 名成员参与了 {A} 次协作行为，覆盖 {W} 个自然周。

CSM 可编辑叙事文本，不可修改指标（沿用 v0.1 快照机制）。

## 8. 与呈现层的衔接（说明性，实现另行排期）

- **前端（v017_value）**：置顶「价值亮点」区；指标卡按四轴分组；环比徽章按 `isImprovement` 着色（改善绿↑ / 退步红↓ / 持平灰 / 新增 / 未知），不是按数值方向；补画协作周趋势与迭代完成周趋势（后端已有数据）；报告头部展示「统计范围」背景行。
- **PDF（renderValueHighlights）**：价值亮点 section 置于价值摘要之后；分组 rows 增加环比列；需关注段按 CSM 选择包含。
- **API 无需变更**：metrics 经快照整体透传，新增维度随快照结构自然下发。

## 10. 开放评审点
